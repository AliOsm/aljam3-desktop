The audit reviewed all tracked application, patch, packaging, workflow, test, benchmark,
documentation and asset files. Relevant Scarpe/PDFium internals were inspected where
failures crossed into dependencies. The final application inventory contains 325 tracked
files and 24,064 text lines, including 119 Ruby source/scripts. This report and its evidence
archive are additional audit outputs. All 140 literal relative-require paths resolve.
Bundled asset validation decoded 149 image/vector/icon/font files. Binary files were
inspected using decoders and package manifests rather than described as line-by-line code.

Twenty-four findings were addressed individually. These include application defects,
performance problems and validation-tool defects; they are not 24 independent crashes.
The existing PDFium cancellation patch was also exercised extensively. An earlier long
run failed and exposed a further image-export defect (F023); it is recorded as a failure.

VALIDATION

Application and native tests:
  - Final packaged platform suites: macOS 148 tests / 793 assertions; Windows 150 tests /
    808 assertions. Both have zero failures, errors or skips.
  - Final Linux suite: 148 tests / 812 assertions, zero failures, errors or skips.
  - Native Rust suites: 301 tests passed on Linux/macOS and 300 on Windows.
  - 557 alignment checks cover light/dark themes, three window sizes and multiple scale
    factors. Native interaction, feedback, motion, text selection and scrollbar checks passed.
  - All 119 Ruby files and the workflow YAML parse; whitespace and relative-path checks pass.
  - Patch setup was tested repeatedly and against fresh pinned source; it is idempotent.

PDF cancellation, seeking and recovery:
  - 361 subprocess-isolated fault cases passed across image streams, nested page trees
    and a real PDF. Cancellation checkpoints, file-access callbacks and HTTP block reads
    were failed individually. The original Ruby errors survived, failed renders left no
    cached PNG, and successful retries matched local-reference pixels.
  - Packaged-runtime tests interrupt 20 reader navigation/zoom cycles inside image reads
    and verify that the latest requested page and zoom win. Mac packages are retested on
    macOS 26 using the exact archived app, not a rebuilt replacement.
  - The report records the loaded PDFium path, SHA-256 and patch fingerprint. A stale
    fingerprint fails verification; the cache key includes both native patches.
  - Live book 3435 / file 8291 / page 104 fetched 504,686 of 8,500,078 bytes (5.94%) in
    eight HTTP ranges with a fresh render/byte cache. A cached reread fetched zero bytes.
    Page 471 fetched 570,222 bytes in nine ranges in the packaged checks.
  - This establishes seeking for those documents. Some PDFs legitimately require more
    bytes because of their structure or resources; it is not a universal byte ceiling.

Data durability and offline use:
  - Six real-native restart tests covered graceful exit and forced kill during a partial
    PDF, after text indexing and after final directory rename. Exact bytes and searchable
    pages recovered in all cases, including Arabic data-directory paths.
  - Five forced process kills during schema v1/v3 upgrades preserved all 2,000 fixture
    pages. The next launch completed migration with search/history/bookmarks intact.
  - The live native flow performed 31 checks against the API and a real book, then
    downloaded, read, searched and removed its offline copy.
  - Live PDF/TXT/DOCX exports were checked for their extensions and actual content.
  - Forced image-cache eviction: 65 native cycles, 1,457 assertions and 13 successful
    image exports after deleting their render caches. Existing destinations survived
    simulated disk-write failure; retry used the original page after navigation.

Large-library correctness and performance:
  - A fresh fixture contains 63,528 named books and 1,000,000 pages in a 3,487,121,408-byte
    SQLite database. The pages repeat 7,031 real OCR samples deterministically; they are
    not one million unique real pages or a full download of the library.
  - Independent full match counts, selected scopes, sampled contents, six relevance pages
    and six library-order pages passed. Search cancellation took 3.06 ms; concurrent page
    reads had a measured maximum of 0.19 ms in that run.
  - Two thousand randomized search/download-state operations matched an independent FTS
    reference, including query syntax, combined scopes, eligibility, paging and reopening.
  - Native app checks passed with the million-page fixture, including author content
    searches returning exactly 7,530 and 421 matches, cancellation, reading and Find.
  - Paired sparse-author timings: common word 12.27 -> 2.25 s; two words 3.90 -> 0.34 s;
    rare word 0.45 -> 0.10 s. All complete result objects were identical. Broad-library
    and unfiltered timings stayed around 2.5–3.2 s in those individual trials.
  - Native broad-search wall times were about 2.2–3.0 s in the final UI run; scoped common
    search was 3.36 s and scoped multiword search 0.37 s. These are workload observations,
    not latency guarantees. Background audit work and OS caches affect the measurements.
  - The historical 37.6-million-page / 127 GB fixture was not rebuilt in this audit because
    of available disk space. Its earlier results remain in bench/results and are labelled
    separately. Seven empty source catalog rows were excluded from new fixtures.
  - The accepted first-10,000 eligible matching pages policy is unchanged. All query words
    still match; filters and completed-download eligibility apply before candidate selection.
    Expanding the pool may reorder relevance results. Library-order search remains uncapped.

API follow-up:
  - PR https://github.com/ieasybooks/aljam3-web-app/pull/176 adds file_id to page results.
    Existing response fields, filters and matches are unchanged; no migration or reindex.
  - All 418 backend examples passed with 100% configured line and branch coverage. Security scan,

  - Deployment https://github.com/ieasybooks/aljam3-web-app/actions/runs/37238333158 passed.

REMAINING LAUNCH ITEMS AND LIMITS

1. The test Mac app is ad-hoc signed and not notarized. Windows executables are unsigned.
   Production signing/notarization remains before a public launch.
2. At the owner's request, the repository was made public and the standalone Thmanyah
   license file was removed. Embedded font metadata was not changed. Deleting a notice
   does not establish redistribution permission; permission or an open-licensed heading
   font remains an unresolved launch item.
3. Automated native headless and ghost runs exercise the real app, renderer, workers and
   packaged runtimes, but are not a physical-device acceptance pass. Actual Arabic keyboard
   layouts, mouse side buttons, expanded macOS save panels, localized shortcuts and
   VoiceOver/Narrator still need interactive checks on target machines. Windows 10 hardware
   and older supported macOS versions were not available in this audit.
4. PDFium remains in the application process. The cancellation/read-failure path is fixed
   and regression-tested; arbitrary malformed native documents may still expose other
   library defects. Process isolation would be a separate hardening project.
5. Offline rankings use the agreed bounded pool and can omit a better result outside it.
   This is the documented product decision, not a newly discovered correctness failure.
6. This audit cannot prove the absence of every possible defect. Confirmed failures found
   here were reproduced, fixed and retested; the evidence distinguishes passing runs,
   failed exploratory runs, synthetic scale fixtures and live-service checks.
